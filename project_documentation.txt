SECTION 1: PROJECT OVERVIEW
----------------------------------------------------------------

Project Title:
  Smart Secure Student Attendance Management System (SmartAttend)

Version:    2.3
Platforms:  Web App (React + Node.js) + Android App (Kotlin)
Database:   PostgreSQL
Status:     Active Development
            - Web platform: Feature-complete
            - Android platform: Core-complete; sensor integrations pending

Problem Statement:
  Traditional paper-based and manual attendance systems are
  time-consuming, error-prone, and susceptible to proxy fraud.
  Teachers have no real-time visibility, administrators lack
  consolidated reports, and students cannot track or dispute
  their own records.

Solution:
  SmartAttend is a multi-role, multi-platform attendance
  management system that provides:
    - Secure session-based attendance (QR code + alphanumeric code)
    - Browser/camera face verification (TensorFlow.js)
    - GPS geo-fencing to confirm physical presence on campus
    - Role-based dashboards for Students, Teachers, and Admins
    - Real-time notification system (in-app + Firebase FCM)
    - Correction request workflow with approval / rejection
    - Full audit trail and advanced analytics with charts

Android Launch Flow:
  SplashActivity (LAUNCHER)
    ↓ 2s animated entrance
    ├── token present → MainActivity (role-based nav graph)
    └── no token     → HomeActivity (Student / Teacher / Admin cards)
                           ↓ card tap
                         LoginActivity (pre-fills demo creds in debug)

Data Flow — Marking Attendance (Web):
  1. Student opens Mark Attendance page
  2. useFaceDetection hook loads TensorFlow.js model
  3. useGeolocation hook fetches GPS coordinates
  4. Student selects active session or enters code
  5. FaceCapture component verifies a face is detected
  6. POST /api/student/attendance/mark → backend validates:
       a. Session exists, is active, not expired
       b. Student belongs to the session's class
       c. Not already marked for this session
       d. GPS within campus geo-fence radius
  7. Attendance record created; anomaly logged if suspicious
  8. In-app notification created for student

Data Flow — Teacher Session (Web / Android):
  1. Teacher selects subject + type, sets duration
  2. POST /api/teacher/sessions → row created with
     alphanumeric code, QR data, expires_at computed
  3. Students poll GET /api/student/sessions/active (~5s)
  4. Teacher clicks Stop → DELETE /api/teacher/sessions/:id
  5. is_active set false → students' next poll gets empty list

SECTION 5: DATABASE SCHEMA
----------------------------------------------------------------

Table: users
  id (UUID PK), name, email, password_hash, role
  (admin|teacher|student), profile_photo (base64 text), phone,
  fcm_token, is_active, created_at

Table: branches
  id (UUID PK), name, code, created_at

Table: classes
  id (UUID PK), name, section, year, branch_id (FK→branches),
  created_at

Table: teachers
  id (UUID PK), user_id (FK→users UNIQUE), department,
  employee_id, created_at

Table: students
  id (UUID PK), user_id (FK→users UNIQUE), roll_number,
  class_id (FK→classes), created_by (FK→teachers), created_at

Table: subjects
  id (UUID PK), name, code, class_id (FK→classes),
  teacher_id (FK→teachers), created_at

Table: attendance_sessions
  id (UUID PK), subject_id (FK→subjects), teacher_id,
  class_id, session_code (unique text), qr_data (text),
  session_type (QR|Code|Secure), latitude, longitude,
  radius_meters, is_active (bool), created_at, expires_at

Table: attendance
  id (UUID PK), student_id (FK→students), subject_id,
  session_id (FK→attendance_sessions), status
  (present|absent|late|manual), marked_at, latitude, longitude,
  face_verified (bool), is_manual (bool), marked_by (FK→users),
  created_at

Table: attendance_requests
  id (UUID PK), student_id, subject_id, request_date, reason,
  status (pending|approved|rejected), reviewed_by (FK→users),
  review_note, created_at, updated_at

Table: notifications
  id (UUID PK), user_id (FK→users), title, message, type,
  is_read (bool), created_at

Table: anomaly_logs
  id (UUID PK), student_id, subject_id, session_id,
  anomaly_type, description, created_at

Table: audit_logs
  id (UUID PK), user_id (FK→users), action, entity_type,
  entity_id, details (JSONB), ip_address, created_at

Table: password_reset_otps
  id (UUID PK), user_id (FK→users), otp_code, expires_at,
  is_used (bool), created_at

SECTION 10: ANDROID — DETAILED STATUS & ARCHITECTURE
----------------------------------------------------------------

Architecture Pattern: MVVM + Hilt Dependency Injection

App Entry Flow:
  SplashActivity is the declared LAUNCHER activity.
  On launch it shows a 2-second animated splash, then:
    - Token found in DataStore → navigates to MainActivity
    - No token              → navigates to HomeActivity

  HomeActivity presents role-selection cards (Student / Teacher /
  Admin). Tapping a card opens LoginActivity with the selected
  role pre-populated (debug builds also pre-fill demo credentials).

  MainActivity is the NavController host. After verifying the
  session it loads the role-appropriate navigation graph and
  bottom navigation menu. An overflow menu in the toolbar
  provides a Logout option that clears the DataStore session
  and returns to HomeActivity.

Navigation Graphs:
  nav_student.xml → Bottom nav: Dashboard, Mark Attendance,
    History, Requests, Notifications, Profile
  nav_teacher.xml → Bottom nav: Dashboard, Students,
    Attendance, Sessions, Reports, Requests, Profile
  nav_admin.xml   → Bottom nav: Dashboard, Students,
    Teachers, Classes, Subjects, Analytics, Audit Logs, Profile

Local Storage (DataStore):
  PreferenceManager.kt defines `Context.dataStore` (name:
  "smartattend_prefs"). Stored keys: auth_token, user_id,
  user_name, user_email, user_role, profile_id, class_id.
  TokenManager.kt reads the token synchronously (runBlocking)
  for use in SplashActivity before the coroutine scope is ready.

Dependency Injection (Hilt — AppModule.kt):
  - Provides: OkHttpClient (with AuthInterceptor + logging),
    Retrofit instance (BASE_URL from BuildConfig), ApiService
  - AuthInterceptor injects "Authorization: Bearer <token>"
    from PreferenceManager on every outgoing request

Data Repositories:
  - AuthRepository:    login, register, forgotPassword, verifyOTP,
    resetPassword, getProfile, updateProfile, changePassword,
    uploadProfilePhoto, updateFcmToken, getUserName
  - StudentRepository: dashboard, attendance history, subjects,
    activeSessions, markAttendance, requests, notifications
  - TeacherRepository: dashboard, subjects, students (CRUD),
    sessions (create/stop), manualAttendance, reports, requests,
    low-attendance alerts
  - AdminRepository:   system stats, students, teachers, classes,
    subjects (CRUD), analytics, audit logs

Android BASE_URL Configuration (app/build.gradle):
  Debug (emulator):   http://10.0.2.2:5000/api/
  Release:            https://<your-replit-domain>/api/

Remaining Android Integrations:
  - ML Kit Face Detection in MarkAttendanceFragment
  - ZXing QR scanner in MarkAttendanceFragment
  - FusedLocationProviderClient in MarkAttendanceFragment
  - Admin: Create / Edit dialogs for Students and Teachers
  - Admin: Advanced Attendance Analytics deep-dive screen

SECTION 11: PLATFORM SYNCHRONISATION
----------------------------------------------------------------

Session Lifecycle:
  Teacher starts session (web or Android):
    → POST /api/teacher/sessions creates is_active=true row
    → Students poll GET /api/student/sessions/active (~5 s)
    → Session card appears on student screen
  Teacher stops session:
    → DELETE /api/teacher/sessions/:id sets is_active=false
    → Students' next poll returns empty list → card removed

Server-Authoritative Validation:
  - Expired sessions (expires_at < NOW()) cannot be marked
  - Client countdown timers are cosmetic only
  - All constraints (geo-fence, face, class membership) enforced
    server-side on POST /api/student/attendance/mark

Notification Flow:
  - Any action (request approve, alert, session start, etc.)
    calls notificationService.js to create a DB notification row
  - Web: NotificationBell polls /api/notifications/unread-count
  - Android: FCMService.kt receives push if credentials are set
  - Fallback: In-app notification list always reflects DB state

SECTION 12: KNOWN LIMITATIONS (DEVELOPMENT MODE)
----------------------------------------------------------------

1. DROP TABLE on restart — server/db/database.js recreates all
   tables on every start. All data is wiped. Remove before prod.

2. OTP delivery — OTP is printed to stdout (server console).
   Configure nodemailer with real SMTP for email delivery.

3. Firebase FCM — Admin SDK is initialised but requires real
   FIREBASE_PROJECT_ID, FIREBASE_CLIENT_EMAIL, and
   FIREBASE_PRIVATE_KEY env vars for actual push delivery.
   In-app notifications work without Firebase credentials.

4. CORS — Currently allows all origins. Restrict to your
   production domain before deployment.

5. JWT_SECRET — Falls back to a hardcoded dev string.
   Always set a strong random secret in production.

6. Profile photos in DB — Stored as base64 TEXT. Fine for demo;
   migrate to object storage (S3 / Cloudflare R2) for production.

7. No pagination — Notification and attendance endpoints return
   all records. Add LIMIT / OFFSET for large datasets.

8. Android sensor integrations — ML Kit face detection, ZXing
   QR scanner, and FusedLocation are declared in build.gradle
   but not yet wired into MarkAttendanceFragment logic.
